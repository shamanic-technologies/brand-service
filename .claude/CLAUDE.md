## An org's brand identity is its FIRST claim, and it is answered by an indexed batch read — never by the full catalogue

`POST /internal/brands/identity-by-org` (`src/services/orgBrandIdentityService.ts`) answers "what brand identity belongs to these orgs?" — a display `name` plus the `domain` a logo is rendered from, and nothing else. The consumer (billing-service, naming the org whose conversion earned a pending referral reward) is showing a customer who referred them, not opening a window onto another customer's business, so **never widen this payload** with money, campaigns, performance, configuration, prospect PII, audiences, or the brand's other orgs.

**It is a BATCH read, and it must stay one indexed query.** `GET /internal/brands/all` is the whole-catalogue staff listing; answering one org from it is the bulk-reader antipattern — the work grows with the platform and is almost entirely wasted. `getBrandIdentitiesByOrgIds` is a single `DISTINCT ON (org_id)` over `org_brands` (hitting `org_brands_org_id_idx`) joined to `brands`, bounded by the ids asked for. Do not reimplement it on top of the catalogue listing, and do not let a caller fan out one request per org.

**An org with several brands resolves to the one it claimed FIRST** — `org_brands.claimed_at` ascending, ties broken by `brand_id` ascending so the order is total even when two claims share a timestamp. The first claim is the brand the org onboarded with, and the pick is *stable*: every brand claimed later leaves the answer untouched, so a referral reward keeps naming the same business for the life of the row. A "most recent" or "any" pick would let the displayed name drift under a customer looking at a months-old reward.

**Absence is the answer for an org with no brand.** No entry, no placeholder, no empty string — the caller renders nothing rather than something wrong. `resolveDisplayName` returns a stored name, else the titlecased domain (a deterministic derivation of data the brand actually has), else `null`; a row that identifies nothing is filtered out in SQL so the org still resolves via its NEXT claim rather than being lost to an unidentifiable first one. Do not add an `'Unknown'`-style fallback here.

**Internal only.** Service auth, org-less, deliberately not on `publicRouter` and not org-scopable by a customer — the caller legitimately holds org ids that are not its own. The batch rides in the BODY, not a query string, so org ids do not land in access logs and proxy traces. Regression: `tests/integration/orgBrandIdentity.test.ts`, `tests/unit/orgBrandIdentity.test.ts`.

## A domain belongs to whoever CHECKED OUT on it — brand-service never computes checkout itself

Owner decision (Kevin, 2026-07-29). `brands.domain` is globally unique, so attaching a website to a brand can collide with an existing holder row. The collision is NOT automatically a refusal:

- **Holder never checked out (by ANY org)** → the domain is up for grabs. It is MOVED onto the target brand; the holder is left as a **no-website brand** (`domain = url = NULL`) so any OTHER org still claiming it keeps a working identity. Never delete a holder row, never touch another org's `org_brands` membership.
- **Holder checked out by the CALLER's org** → 409 `DOMAIN_OWNED_BY_YOUR_PAID_BRAND`.
- **Holder checked out by ANOTHER org** → 409 `DOMAIN_OWNED_BY_ANOTHER_ORG`.

The two refusals MUST stay distinguishable by `code` (plus `domain` + `conflictingBrandId` on the body) — a dashboard renders different copy per case ("switch to your paid brand" vs "this domain isn't yours"). Do NOT collapse them back into one generic `DOMAIN_CONFLICT`.

**Checkout state is NOT ours to compute.** client-service owns the (org, brand) ↔ money join and derives it live from stripe + billing: `GET /internal/brands/{brandId}/checkout-status` → `{ brandId, status: 'checked_out'|'not_checked_out'|'no_org_claims_brand', checkedOut, orgs: [{ orgId, checkedOut, reason, ... }] }`. The paying orgs are the `orgs` entries with `checkedOut: true`. Never re-derive this from billing/stripe here, and never mirror it locally. Client: `src/lib/client-client.ts` (`CLIENT_SERVICE_URL` / `CLIENT_SERVICE_API_KEY`).

**Fail CLOSED, never fail open.** A network error / non-2xx / unparseable body from client-service throws `CheckoutStatusUnavailableError` → the route 502s. Defaulting to "nobody paid" would hand a paying org's domain to somebody else. There is deliberately no `?? false`, no 404-means-unpaid branch (client-service answers never-paid with a truthful 200, so a 404 means the route is wrong, not that the brand is free).

**Cleanup uses the EXISTING merge primitive** — `rewriteBrandReferences` in `src/services/brandMergeService.ts` (moved there out of `brands.routes.ts` so services can call it without importing a router). When the never-paid holder belongs to the CALLER's own org, its child rows are merged onto the target (target always wins on conflict) and the caller's `org_brands` row is deleted, so the abandoned shell stops polluting their brand list. The primitive now also carries the user-authored one-row-per-brand tables (`brand_business_context`, `brand_sales_economics`, `brand_click_destinations`, `brand_whatsapp_links`) and `brand_user_fields` — without them a merge silently strands confirmed user data on the abandoned row. `brand_transfers` (audit log) and `brand_relations` (PK(source,target), a rewrite can self-collapse an edge) are deliberately NOT rewritten. Reference: `tests/integration/domainTakeover.test.ts`.

## No-website brand identity is `(orgId, lower(name))` — creates are idempotent

A no-website brand has no domain to dedup on, so `createBrandWithoutWebsite` keys on the caller's org + the case-insensitive name and RETURNS the existing brand (`created: false`) instead of inserting. Re-running onboarding used to mint a fresh row every time — that is how one org accumulated three brands for one business. Two different names for one org stay distinct; two orgs with the same name stay distinct (no cross-org reuse — there is no shared domain identity to justify it). Regression: `tests/integration/noWebsiteBrandDedup.test.ts`.

## A brand's share credential is ABSENT by default, unguessable, and NEVER the conversion-tracking token

`brand_share_tokens` (PK = `brand_id`, `token` text NOT NULL UNIQUE, `org_id` uuid NOT NULL) holds the per-brand read-only SHARE credential: a customer mints one so somebody outside the org (investor, client, colleague) can open a read-only public brand page without signing in. Owner: `src/services/brandShareTokenService.ts`; routes: `src/routes/share-token.routes.ts`.

**Absent by default.** No row is created at brand create. A brand with no row is NOT shareable and nothing resolves — absence IS the state, so there is no `enabled` flag and no null-token row.

**One row per brand, so rotate/revoke are the row's own semantics.** Rotating overwrites `token` in place — that single UPDATE is exactly what makes the previous link stop resolving. Revoking DELETEs the row. Never add a second live credential per brand (a `SELECT ... WHERE token = $1` must stay a one-row exact match, and "rotate stops the old link" must stay true by construction, not by a sweep).

**The credential must not be derivable from anything the customer already exposes.** The brand id and the org id both sit in the customer's own address bar and in every support ticket they paste, so a link built from either is a one-line transform of a public string. `generateShareToken()` takes NO arguments: `bshr_` + `randomBytes(32).toString('base64url')`. Do not "improve" it into an HMAC/hash of the brand id, do not seed it from the clock, and do not encode the org id in it — the token stays an opaque random string, and everything a resolve answers with comes from the ROW it matches, never from the string. Regression: `tests/unit/brandShareToken.test.ts` pins the zero-arg signature + entropy.

**`org_id` records WHICH ORG SHARED THE BRAND, and it is written at MINT time, never derived on read.** The renderer of a shared page needs it because every figure such a page shows (outreach, audiences, leads, strategy) is served per-org — the credential alone tells it which brand to render and leaves it unable to fetch a single number. It cannot come from `org_brands`: 21 production brands are claimed by MORE than one org and 18 by NONE, so membership answers "ambiguous" or "nothing" exactly where one org is needed. The mint route is org-scoped and ownership-checked, so the writer already holds the answer — persist it (`createIfAbsent(brandId, orgId)` / `rotate(brandId, orgId)`, arity pinned by the unit test), do NOT add a read-time lookup or a fallback. **A rotate re-mints, so the row's org becomes the ROTATING org**: for a brand two orgs both claim, the link that resolves is the one minted last and it opens ITS view. The column is NOT NULL on purpose — the resolve must answer with one org or refuse, and a nullable column invites exactly the plausible-stand-in fallback this must never serve. Migration `0048` backfills legacy rows from the earliest `org_brands` claim (verified on a fork of production: the one pre-existing row attributed correctly, zero nulls, re-run idempotent).

**Do NOT reuse or extend the conversion-tracking token (lead-service).** That one is a WRITE credential for conversion ingest; putting it in a shared URL would let the link holder forge conversions. These are different credentials with different blast radii and must stay separate.

**The resolve is service-auth, takes no org IN, and answers with the org OUT.** `POST /internal/share-tokens/resolve` body `{ shareToken }` → `{ brandId, orgId, brand }`. It takes no org context by design (the caller is distribute's own server-side public-page renderer, which has not identified an org yet) and answers with one because learning it is the whole reason the renderer calls: `orgId` sits at the TOP LEVEL beside `brandId`, never inside `brand`, so the public brand payload is untouched and nothing a broader audience reaches gained a field. Service auth is enough — this deliberately is NOT reachable unauthenticated from the internet. The credential rides in the BODY, not the path, so it does not land in access logs and proxy traces. Unknown / revoked / rotated-away all return the same 404.

**`brand` is `getBrandDetail(..., { mode: 'platform' })` — the exact shape `GET /public/brands/:id` already serves.** Nothing new is exposed. Never widen this payload with money (spend, daily budget, cost per outcome, ROI, credits), prospect PII (lead names/emails), audiences, or the org id. If the public page needs more, it composes it from endpoints it already calls — a share credential does not unlock new data classes.

**NOT rewritten by `rewriteBrandReferences`** (the merge primitive), alongside `brand_transfers` / `brand_relations`. Moving a credential minted for an abandoned holder onto the target brand would silently widen what every existing link holder can see; the credential stays with the brand it was minted for. Regression: `tests/integration/brandShareToken.test.ts` (full lifecycle + cross-org 403 + "a credential minted for brand A never resolves to brand B" + a brand two orgs claim, where the credential names whoever minted it).

## `brands.current_goal` is the ONE authority on a brand's goal — `optimization_goal` is a SPELLING, not a second field

**The resolution rule, in one line: `brands.current_goal` answers what a brand optimizes for, always; `brand_sales_economics.optimization_goal` only records the RAW WIRE SPELLING the caller sent, and is consulted solely to tell two spellings that share ONE runtime goal apart.** The two can no longer answer differently because there is only one answer plus a spelling for it. Concretely, `formatSalesEconomics` takes `currentGoal` as a **REQUIRED** parameter and always derives from it; the optional-`currentGoal` fall-back that read the stored column *as if it were a goal* was the single place the two fields could contradict each other, and it is gone. Never re-add a read path that treats `optimization_goal` as a goal source, and never add a THIRD store for the concept.

Only two spellings are ever recovered from the column (`resolveWireOptimizationGoal`): `form_submissions` under the `signup` runtime goal, and `website_purchase` under `purchase`. Everything else collapses to the base wire value. On WRITE, an `optimizationGoal` PUT is mapped to `CurrentGoal` and persisted on `brands.current_goal`; the column is mirrored so the sub-type spelling round-trips. `CurrentGoal` is the vocabulary **features-service** consumes for runtime candidate selection.

**One emitted vocabulary.** `sales_meetings` (the dashboard's local spelling of the booked-meeting goal) is ACCEPTED ON WRITE — it maps to `meetingBooked` like `booked_meetings` does — but brand-service NEVER emits it: every read of a booked-meeting brand answers `booked_meetings`, and it is deliberately NOT a recoverable sub-type. Accepting an alias at the source kills caller drift without giving brand-service a second thing to say. Add an accept-only alias the same way: the `LegacyOptimizationGoal` type + `OptimizationGoalSchema` + a case in `legacyOptimizationGoalToCurrentGoal` ONLY — never in `currentGoalToLegacyOptimizationGoal`, never in `resolveWireOptimizationGoal`, never in the CHECK constraint.

**Two kinds of new `optimizationGoal` value — pick the pattern:**

**Pattern A — a value that needs its OWN runtime behavior** (features-service must select candidates differently). It gets a dedicated `CurrentGoal`. REQUIRES all together (or GET returns the wrong goal / a mapping switch throws):
1. `OptimizationGoalSchema` + `OptimizationGoal` type (schemas.ts + salesEconomicsService.ts) — new legacy value.
2. `CurrentGoalSchema` + `CurrentGoal` type + `CURRENT_GOALS` + `LegacyOptimizationGoal` type + BOTH mapping switches (`legacyOptimizationGoalToCurrentGoal` / `currentGoalToLegacyOptimizationGoal`) in `brandGoalService.ts` — new canonical value (switches are exhaustive; a missing case fails `tsc`). **This makes features-service/campaign-service see a NEW runtime value — only do it if they can handle it.**
3. The `brands_current_goal_check` DB CHECK constraint (schema.ts) — widen the `IN (...)` list, via an additive migration (drop-if-exists + re-add). Else the write 23514s.

Reference: PR #317 (`website_visits`/`positive_replies` + single-step rate fields).

**Pattern B — a value that is a WIRE-ONLY SUB-TYPE of an existing runtime goal** (same outreach behavior — e.g. `form_submissions` behaves like `signups`: same visit→micro-conversion→paid family). It maps to the EXISTING `CurrentGoal`, so runtime consumers never see a new value AND no CHECK-constraint change is needed. But because two wire values now share one `CurrentGoal`, the derive-from-`current_goal` read can't distinguish them — so the STORED `optimization_goal` column becomes authoritative for the sub-type (it is NO LONGER "effectively ignored" for these). REQUIRES:
1. Add the value to `OptimizationGoalSchema` / `OptimizationGoal` / `LegacyOptimizationGoal` and give `legacyOptimizationGoalToCurrentGoal` a case returning the EXISTING `CurrentGoal` (do NOT touch `currentGoalToLegacyOptimizationGoal` / `CurrentGoal` / the CHECK constraint).
2. Preserve the RAW wire value on `brand_sales_economics.optimization_goal` in `upsertByBrandId` (store `metrics.optimizationGoal` when supplied; conditional-set on update so an omitted goal preserves it — else a metrics-only PUT collapses it back).
3. Recover it on the ORG (dashboard) read via `resolveWireOptimizationGoal(currentGoal, storedColumn)` (`formatSalesEconomics(..., wireOptimizationGoal=true)`, threaded from `getByBrandId({wireOptimizationGoal:true})` — org GET + PUT response). The INTERNAL (campaign-service) read keeps the default (`false`) so it collapses to the runtime-safe base value and downstream runtime consumers never see the sub-type.

Reference: PR #322 (`form_submissions` → `signup` runtime goal + two-step rates `visitToFormSubmissionPct`/`formSubmissionToPaidClientPct`).

**Wire-token COLLISION rule — NEVER repurpose an existing wire value, even when a DISPLAY rename "frees up" its word for a NEW goal.** When product renames goal X's display name and the freed word is ALSO the wire token of an EXISTING goal Y (e.g. renaming "purchase" → "website purchase" while adding a NEW combined goal displayed "Sales" — and the wire token `sales` already means the OLD purchase goal), do NOT reassign the wire token `sales` to the new goal. Doing so silently reinterprets every stored `sales` (old-purchase) brand as the new goal AND breaks the transition window (the old dashboard still sends `sales` for old-purchase). Instead, the SAFE triad:
1. Keep the existing wire token meaning its OLD goal FOREVER (backward-compat + it's what the internal read emits) — `sales` stays → `purchase`.
2. Give the RENAMED goal a NEW preferred wire spelling as a Pattern-B sub-type of its unchanged canonical — `website_purchase` → the EXISTING `purchase` current-goal (canonical + runtime behavior untouched, so features-service/campaign-service never see a new value; org read recovers `website_purchase` via `resolveWireOptimizationGoal`, internal read collapses to `sales`).
3. Give the NEW goal a BRAND-NEW token the old dashboard never sends, as a Pattern-A dedicated goal — `combined_sales` / `combinedSales`. This is what guarantees no collision: the new goal's token is disjoint from every stored value, so no purchase-brand is ever reinterpreted.
Do NOT rename the canonical `CurrentGoal` for a pure display-rename whose runtime behavior is unchanged (renaming `purchase`→`websitePurchase` would force features-service/campaign-service to accept a renamed runtime value for existing brands — a gratuitous cross-service break). The rename lives at the wire/display layer; the canonical token + stored rows stay put (migration is an additive CHECK widen only, zero row rewrite → existing brands byte-identical). Reference: PR #346 (combined "Sales" goal `combined_sales`/`combinedSales` reusing the existing reply→paid + visit→paid rates, + "website purchase" rename via `website_purchase` sub-type of `purchase`; `sales` stays backward-compat). Regression pattern: `tests/unit/salesCombinedGoal.test.ts` (explicit collision-safety asserts).

**Goal-family rates MUST be NOT NULL with server defaults — a nullable goal rate breaks the fail-loud consumer.** The form-submission rates shipped nullable in #322, but features-service reads the EFFECTIVE (Gold) layer for a `form_submissions`-goal brand and fails loud (502) on an absent/null rate — so a nullable rate that the effective layer omits = prod-broken for every such brand. The rates were made NOT NULL with DB defaults `25 / 20` (mirroring the `visitToSignupPct`/`signupToPaidClientPct` two-step pair, since `form_submissions` collapses to the `signup` runtime goal), and the effective layer (`SalesEconomicsAverages` + `getEffectiveByBrandId` user branch + `getAverageAcrossBrands` MEAN + `SalesEconomicsEffectiveResponseSchema`) now serves them as real numbers for ALL provenances (`user`, `cross-brand-average`) identically to the single-step rates. **RULE: any conversion rate tied to an optimization goal must be a NOT NULL column with a server default AND must be carried on the effective serving layer — never nullable, never omitted from `economics`.** A goal rate present on the saved layer but absent from the effective layer is the exact bug that 502'd form_submissions brands. Reference: PR #324 (migration 0038 — backfill + SET DEFAULT/NOT NULL; effective layer + schema extended).

## Sales FUNNELS (`brand_sales_funnels`) — the declared SET, per-funnel economics, and why it is a separate table from `brand_sales_economics`

A brand sells through SEVERAL funnels, and each one is priced on its own. A funnel is one chain from the first signal outreach can buy (a positive reply, or a click onto the site) down to a paid client, and it owns everything that chain needs priced: the conversion rate of each of its legs, the lifetime revenue of a client won through it, the page an outreach click lands on and — when a meeting sits in the chain — a booking link. `salesFunnelCatalogue.ts` owns the four funnels (`reply_meeting`, `visit_meeting`, `visit_signup`, `visit_form`) and is deliberately byte-equal with the dashboard's `apps/dashboard/src/lib/sales-funnels.ts` (keys, chains, legs) so the screen and the store describe ONE model. **The consumer is the ground truth for the model** — when the card gains a funnel or a leg, the catalogue follows it, not the other way round.

**Declaration is explicit and is the ONLY way this is known.** A funnel exists for a brand because the brand said so (a row in `brand_sales_funnels`, PK `(brand_id, funnel_key)`), and every number on it is a number the brand gave us (a non-null column). There is NO defaulting layer here — no cross-brand average, no seeding from `brand_sales_economics`, no "0 means unset". **Every value column is NULLABLE with NO server default, and that is load-bearing**: it is the only thing that lets a consumer tell "the brand declared 0%" from "the brand never told us". This is exactly what `brand_sales_economics` cannot express — every rate there is NOT NULL with a server default (deliberately, so the fail-loud consumers never read a null), so a brand that configured nothing still reads back plausible-looking numbers and **the set of funnels a brand runs can NEVER be derived from its stored economics**. Do not try, and do not synthesize a set. An empty `funnels` array is not self-explanatory: it means two opposite things depending on `declared`, and the `declared` rule below is how to read it.

**Two homeless values live ONLY here**: `meeting_booked_to_attended_pct` (the meeting show-up rate, mid-chain in both meeting funnels) and `booking_url`. Nothing else in the fleet stores either.

**`declared` is a THIRD state and `brand_sales_funnel_declarations` is its only home — do NOT fold it back into "zero rows".** Zero funnel rows is ambiguous on its own, and the two readings lead to OPPOSITE consumer behaviour: `declared: true` with an empty list is the brand STATING it sells through none (a real answer — the consumer reports it unrankable), while `declared: false` is a producer gap (the consumer must surface it, and must never render it as "sells through nothing" or substitute a plausible set). Row presence on that one-column-per-brand table is the statement. Declaring ANY funnel states the set; undeclaring one does NOT un-state it, because a brand that drops its last funnel has still answered the question. `PUT /orgs/brands/:brandId/sales-funnels { funnelKeys: [] }` is the only way to say "none" and is the reason that whole-set route exists alongside the per-funnel one — it validates the set WHOLE before writing, so a bad member rejects 400 with nothing half-applied. Every read returns `{ declared, funnels }`; never return a bare array.

**A brand we hold nothing for is the THIRD answer and 404s — on the internal read too, which is the one that had to be taught it.** The org read gets this free from ownership resolution; the service-auth read has no org context and so answered a nonexistent brand id with `declared: false`, which says "this brand has never told us anything" about a brand that is not there. That reads to a scheduler as a producer gap to surface and wait on, when what it actually holds is a bad id and no statement is ever coming. Three answers, three responses: stated-a-set, stated-none, no-such-brand — and `declared: false` belongs only to a brand that exists.

**The two layers coexist on purpose.** `brand_sales_economics` stays the brand-wide legacy layer that features-service + campaign-service read in prod TODAY, unchanged — its NOT-NULL-with-defaults contract and its effective/cross-brand-average serving layer are untouched by any funnel work. `brand_sales_funnels` is the per-funnel layer the arbitration path reads. Do NOT "unify" them by making economics nullable (that 502s the fail-loud consumers per the goal-family-rates rule above) and do NOT mirror funnel values back onto economics.

**Write contract**: PARTIAL, like sales-economics — an OMITTED field is left exactly as stored, an explicit `null` CLEARS it back to never-declared. `buildFunnelWrite` names only the columns the patch carried, which is what makes those two cases distinguishable; keep it that way or "leave unchanged" silently becomes "wipe". A patch is REJECTED (400), never cleaned up, when it names a rate outside the funnel's own chain, a destination the funnel has no use for, or declares a website-led funnel on a brand with no website — a silently-dropped field reads back as "never declared", which is a lie. Undeclaring DELETES the row, economics and all: a funnel the brand stopped selling through must not leave numbers behind that a consumer could still rank on.

New user-authored table ⇒ it is carried by `rewriteBrandReferences` (dedupe on `funnel_key`, target wins), like every other one. Regression: `tests/unit/salesFunnels.test.ts`, `tests/integration/salesFunnels.test.ts`.
## Boot: the port binds BEFORE migrations, and a gate — not a wait — is what protects the schema

`src/index.ts` calls `app.listen()` FIRST and runs `migrate()` behind it. Do NOT restore the old `migrate().then(listen)` order, and do NOT reintroduce `process.exit(1)` on migration failure.

**Why.** Neon computes suspend after inactivity and take seconds to resume. Awaiting `migrate()` before `app.listen()` means a deploy landing on a cold compute spends its entire startup budget on the first connection: the port never opens inside Railway's ~30s healthcheck window, the deploy is marked FAILED, and the container produces **no application output at all** — not even "Migrations complete" — because it stalled before any logging. The failure has nothing to do with the code being deployed, which is what makes it expensive: it reads as a flaky deploy, you retry onto a now-warm compute, it passes, and the cause is never found. Reproduced on a cold compute 2026-07-30; keeping the compute awake with a `SELECT 1` for the duration of the deploy made the identical deploy pass unchanged. Production runs `suspend_timeout_seconds: -1` so it does not hit this; the staging branch (`br-late-bar-azf3okfj` / `ep-muddy-shadow-az2cm0t6`) runs 300s and hits it after any idle period.

**Binding first does NOT mean serving early.** `app.use(requireMigrationsReady)` sits above every router and below `/`, `/health`, `/openapi.json` (the three that need no database). Until the migrator finishes, every database-backed route answers **503 `MIGRATIONS_PENDING`** with `Retry-After: 5`. The service refuses rather than answering against a schema it has not verified — the guarantee the old `await` gave is kept, just enforced per-request instead of by blocking the port.

**Retry only the connect phase.** `runMigrationsWithConnectRetry` (`src/lib/boot-migrations.ts`) retries on `ETIMEDOUT` / `ECONNREFUSED` / `CONNECT_TIMEOUT` / postgres.js's pool-acquire `"timeout exceeded when trying to connect"` / `"the database system is starting up"`, walking `err.cause` and `AggregateError.errors` (happy-eyeballs emits one sub-error per resolved address). Backoff `250 → 8000`, ~31s total, none of it on the healthcheck's critical path. A statement-level error (bad SQL, failed constraint, `42P01`) is **never** retried — it is a real migration failure.

**Failure is louder than an exit, not quieter.** On a real failure: the error is logged in full, state flips to `failed`, every database route answers 503 `MIGRATIONS_FAILED` with the detail, and `/health` itself returns **503** so Railway marks the deploy unhealthy and keeps the previous container serving. The process deliberately stays alive: `process.exit(1)` crash-looped against `railway.json`'s `ON_FAILURE` / 10 retries and took the port down with it, so nothing could report why.

`NODE_ENV === 'test'` marks migrations ready at import so the exported app is usable; the integration harness (`tests/helpers/test-app.ts`) builds its own app and has no gate. Regression: `tests/unit/bootMigrations.test.ts`, `tests/integration/migrationGate.test.ts`. Issue: #386. Note #386's own "Fix" section proposes `connect_timeout` + `idle_timeout` postgres.js options — PR #389 disproved both (`connect_timeout: 30` is already the postgres.js default; `idle_timeout` defaults to `null` on postgres.js, so setting it makes idle connections close and costs a fresh TCP+TLS handshake — that advice is node-postgres's, mis-transplanted). Do not re-add either.

### A destructive DROP of a user-data table MUST backfill into its replacement BEFORE the drop — in the SAME migration

When a migration `DROP`s a table that holds **user-authored / confirmed** data (offer fields, sales economics, thesis, confirmed profile values — anything a user validated in the dashboard, not an ephemeral extract cache), the same migration MUST first `INSERT INTO <replacement> SELECT ... FROM <dropped_table>` (mapping renamed keys). Creating the replacement EMPTY and dropping the old table in one PR with NO backfill is silent user-data loss — the read path then falls through to the ephemeral "suggested" layer and every confirmed field renders as amber "AI-suggested". Recovery is only possible inside the Neon PITR retention window (24h) via a point-in-time branch; past that, the data is gone forever.

Enforced by `tests/unit/migrationDropGuard.test.ts`: a new migration dropping a table in `USER_DATA_TABLES` fails CI unless it contains an in-file `INSERT INTO` backfill OR is listed in `ACKNOWLEDGED_DROPS` with a recovery reference. Do NOT edit an already-applied migration `.sql` to satisfy the guard (it changes the drizzle hash → the runtime migrator re-runs/errors); acknowledge historical drops in the test's `ACKNOWLEDGED_DROPS` map instead.

Incident 2026-07-21 (PR #349): `0041_drop_brand_profile_versions.sql` dropped the confirmed-offer-fields table while `0042_brand_user_fields.sql` created the replacement empty with no backfill → 20 brands' confirmed values lost. Recovered post-hoc via `scripts/recover-brand-user-fields-from-pitr.ts` (Neon PITR branch → `brand_user_fields`, `valueProposition`→`dreamOutcome`, idempotent `ON CONFLICT DO NOTHING`, FK-safe).

### A HOTFIX migration is numbered against every branch that exists, and its snapshot must be rebased onto staging's before the sync merges

Two separate traps, both invisible locally, both hit by hotfix v0.60.1 (`0048_brand_share_token_org`, #408).

**Numbering.** The workspace branch is cut from `origin/main`, so the local journal lags staging. `git show origin/staging:drizzle/meta/_journal.json | tail` is necessary but NOT sufficient: a SIBLING CONDUCTOR WORKTREE routinely holds an unpushed migration at the next free number, and nothing on the remote shows it. Check the worktrees too — `ls ~/conductor/workspaces/brand-service/*/drizzle/*.sql | tail` — and take the first number nobody is using. A GAP is fine (the runtime migrator walks the journal in array order; `idx` is informational), a duplicate `NNNN_` prefix is a merge conflict. v0.60.1 skipped to 0048 because staging held 0046 and the `org-scoped-brand-config` worktree held an unpushed 0047.

**Snapshot rebase.** `drizzle-kit generate` on a main-based branch writes a snapshot describing MAIN's schema plus your change — so it does not contain the tables staging added meanwhile. The `.sql` is correct and the hotfix ships fine, but once the sync lands, the next `drizzle-kit generate` on staging diffs `schema.ts` against your snapshot and emits **staging's own tables again as phantom drift** — and whoever hits it has no reason to suspect the snapshot. Fix it ON THE SYNC BRANCH, after resolving the journal (keep BOTH entries, in order): delete your `<n>_snapshot.json`, drop its journal entry, re-run `drizzle-kit generate` (it now diffs against staging's latest snapshot), then **keep only the regenerated snapshot** — rename it to `<n>_snapshot.json`, delete the throwaway `.sql` it emitted, and restore your resolved journal. The regenerated `.sql` is the proof: it must contain ONLY your change (v0.60.1's was the single `ADD COLUMN "org_id"`), which is what confirms no other delta got folded in. Then `drizzle-kit generate` must report **"No schema changes, nothing to migrate"**. The already-applied `<n>_*.sql` is untouched, so the runtime ledger (which hashes the SQL, not the snapshot) never notices.

### A hotfix migration authored on `main` STRANDS every unpromoted staging migration in production — forever, and silently

The runtime migrator applies only migrations stamped ABOVE the last one it recorded. So the moment a hotfix authors a migration on `main` and production applies it, **every migration sitting unpromoted on `staging` with an earlier stamp becomes permanently unreachable in production**: the later promote inserts it into the middle of the journal, below a bar production has already cleared, and it never runs. Staging is fine — it applied them in order — so the two environments diverge with no error anywhere.

It is silent by construction. The journal stays perfectly sorted, `tests/unit/migration-order.test.ts` passes, CI is green (it builds a fresh branch from `schema.ts` and never replays the journal), and the promote succeeds. Nothing reports a pending migration, because from the migrator's point of view there isn't one. The only place the hole exists is production's `drizzle.__drizzle_migrations` ledger, and the only symptom is a `42P01` at runtime on whatever the missing table was — which surfaces on whichever route touches it first, not on deploy.

**Before authoring a migration on a hotfix branch cut from `main`, check whether `staging` holds migrations `main` lacks** — `git show origin/staging:drizzle/meta/_journal.json` against `origin/main`'s. If it does, that hotfix migration will strand them. Either promote first, or accept it and re-create the stranded ones afterwards.

**The repair is a NEW migration, never an edit.** Re-stamping or renumbering the stranded file changes the hash the ledger stores, so environments that DID apply it re-run or error. Copy its statements verbatim into a fresh migration numbered off `main`'s journal tail with a stamp above the last applied one, and rely on the `IF NOT EXISTS` idempotency to no-op where it already ran. Verify against production's ledger directly (`SELECT created_at FROM drizzle.__drizzle_migrations ORDER BY created_at DESC LIMIT 1`) — a stamp is only "high enough" relative to what production actually recorded, not to what the journal says.

Incident 2026-08-01 (v0.61.0 promote → v0.61.1 hotfix): the v0.60.1 hotfix authored `0048` on `main`, applied at `1785509661079`, while `0046_brand_sales_funnel_declarations` sat on `staging` stamped `1785489221879`. Promoting inserted it behind the bar; `brand_sales_funnel_declarations` never existed in production. Both sales-funnel reads 500'd, and so did `rewriteBrandReferences` — the merge primitive behind domain takeover, a customer write path. Repaired by `0049`, which carries `0046`'s statements verbatim.

### Two migration ledgers — never run `pnpm db:migrate` against the shared DB

The runtime migrator (`migrate(db, { migrationsFolder })` in `src/index.ts`, auto-runs at boot) tracks applied migrations in the **`drizzle.__drizzle_migrations`** table (drizzle-orm default schema). But `drizzle.config.ts` points `drizzle-kit` at **`public.__drizzle_migrations`** — a DIFFERENT ledger. So `pnpm db:migrate` would consult an empty/partial `public` ledger and try to replay migrations from scratch against the shared Neon branch (dev+staging). The `IF NOT EXISTS` idempotency means the boot-time re-run is a safe no-op.

### A test that re-implements a DB aggregate must mirror Postgres rounding (`ROUND(double precision)` = half-to-even), and a NEW integration test file can deterministically expose latent cross-file fragility

Two compounding gotchas, observed 2026-06-18 (#272 added `internalPersonas.test.ts`, turned `salesEconomicsEffective.test.ts` red on CI only):

1. **Rounding convention.** `salesEconomicsService.getAverageAcrossBrands` rounds the cross-brand median in SQL: `ROUND(PERCENTILE_CONT(0.5) … )::int`. `PERCENTILE_CONT` returns `double precision`, and Postgres `ROUND(double precision)` rounds **HALF-TO-EVEN** (banker's) — `2462.5 → 2462`. JS `Math.round` rounds **half-UP** — `2462.5 → 2463`. A test that recomputes the expected aggregate in JS must mirror the SQL rounding (use a `roundHalfToEven` helper), or the byte-equality assertion diverges by 1 whenever the value lands on a `.5` tie. This is NOT a product bug — the SQL value is correct.

2. **Schedule perturbation.** The cross-brand-average test asserts over the GLOBAL `brand_sales_economics` set (by design). Adding ANY new integration test file changes vitest's deterministic file-parallelism schedule, which changes which concurrent rows are live during the assertion window — so a previously-hidden `.5`-tie (or any global-aggregate fragility) can flip to a hard, repeatable failure in a PR that never touched the aggregate or its service. When a global-aggregate test fails ONLY on your branch and your diff doesn't touch that table/service, suspect schedule-perturbation exposing a latent test defect (rounding, tie, non-isolation) — fix the test to be robust; do not chase it as a product regression.

When you add a NEW router export (e.g. a fresh `internalRouter` on a route file that previously only exported `orgRouter`), import + mount it in BOTH files, or the integration test 404s on the new path while `pnpm build` stays green (tsc can't see that the route is unmounted). Observed 2026-06-18 (#272 `GET /internal/personas`): mounted only in `index.ts` → every endpoint test `expected 200, got 404` until the same import + `app.use` line were added to `test-app.ts`.

### Unit tests run WITHOUT a DB url — never import a `../db`-importing module into a `tests/unit/*` file un-mocked

`src/db/index.ts` **throws at import time** (`BRAND_SERVICE_DATABASE_URL or DATABASE_URL must be set`) when no DB url is present. The CI `test:unit` step (`vitest run tests/unit`) runs with NO DB url, so any unit test that imports a service/route which transitively imports `../db` makes the whole suite load **`0 test`** and FAIL — even when the imported symbol you actually test is a pure function. It passes locally only because your shell `.env` is loaded. Fix: stub the db module at the top of the unit test — `vi.mock('../../src/db', () => ({ db: {}, brandSalesEconomics: {} }))` (stub just the named exports the module references; `vi.mock` is hoisted above the import). Confirm by running the file with the env unset: `env -u BRAND_SERVICE_DATABASE_URL -u DATABASE_URL npx vitest run tests/unit/<file>.test.ts`. Observed 2026-06-07 (sales-economics-average #211): unit test imported `salesEconomicsService` (→ `../db`) un-mocked; local green, CI `0 test` red; fixed with the `vi.mock` stub.

**Adding a NEW exported symbol to a service that other modules `vi.mock` → grep `tests/` for every `vi.mock('<that-module>'` factory and add the new export to each, or those tests throw `No "<symbol>" export is defined on the mock`.** A `vi.mock(path, () => ({...}))` factory is an EXHAUSTIVE replacement — it only exposes the keys it lists, so a consumer that newly imports your added export from a mocked module blows up at the call site even though the export exists in source + `tsc` is green. The targeted test for YOUR feature passes (it mocks correctly); the breakage is in OTHER tests that mock the same module for a DIFFERENT reason. Cheap pre-push grep: `git grep "vi.mock('../../src/services/<module>'" tests/`. Observed 2026-06-29 (#306 responseSchema): added `buildFieldsResponseSchema` export to `fieldExtractionService`; `multiBrandExtraction.test.ts` + `resetCache.test.ts` both mock that module (for `extractFields`/`getBrand`) and threw `No "buildFieldsResponseSchema" export is defined` until the export was added to both factories.

### No-website brands: pasted business context is the alternative extraction SOURCE

A brand can be created with NO website. `brands.url` and `brands.domain` are NULLABLE (migration `0043`); a no-website brand is created via `POST /orgs/brands { name }` (user-provided display name — the identity, since there's no domain to derive one) and has `url = domain = null`, no domain dedup (each `{ name }` create is a distinct row — two nameless-domain businesses are genuinely distinct). Its field-extraction source is a per-brand free-form text row in **`brand_business_context`** (`content` up to ~1MB, durable/no-TTL), written via `PUT /orgs/brands/:brandId/business-context` (the app raises the JSON body cap to `2mb` for it).

**The source switch lives in `fieldExtractionService.extractFields`:** if `brand.url` is set → scrape+extract exactly as before (unchanged); if `brand.url` is null → read `getBrandBusinessContext(brandId)` and extract from that text (chunked into ≤100k-char "pages" via `chunkBusinessContext` so nothing is sliced by `extractFieldsFromContent`'s per-page cap), skipping map/scrape entirely; if a brand has NEITHER a url NOR business context → **fail loud** (throws `neither a website URL nor pasted business context`), never a fabricated/empty result. `extractFields` reads `brand.url` FRESH on every call, so the **auto-switch when a website is added later rides the EXISTING extraction cache TTL** — once `PATCH /orgs/brands/:brandId { url }` sets the url, the next post-cache-expiry extraction re-sources from the site with NO new cron/TTL. `multiBrandExtractFields` no longer rejects a null-url brand (it delegates the source decision to `extractFields`) and keys its `byBrand`/`byDomain` maps on `brand.domain ?? brandId` (no-website brands have no domain). Consumers of `BrandDetail` (GET `/internal|public/brands/:id`) must handle nullable `url`/`domain`/`logoUrl`/`clickDestinationUrl` — a no-website brand has null for all four; `name` is always non-null. Regression pattern: `tests/unit/noWebsiteExtraction.test.ts`, `tests/integration/businessContext.test.ts`. Reference: PR (this branch).

### Brand name is an INDEX-FIRST priority chain resolved at CREATE (no LLM / Firecrawl / run / cost)

`brands.name` is derived by ONE chain, in this order — each link falls through to the next, the last one can never fail:

1. **logo.dev Search API** (`src/lib/logo-dev-search.ts`, `searchBrandNameByDomain`) — the authoritative company index. `GET https://api.logo.dev/search?q=<domain-or-label>&strategy=match&is_profane=false`, `Authorization: Bearer <secret>`, 3s timeout. Metered on the monthly REQUEST pool (not the Brand-API credit grant), so it is safe per create. **Match discipline: the endpoint is name-to-domain and returns up to 10 fuzzy candidates, so a hit counts ONLY when its `domain` equals the brand's own domain** (www/case-normalized) — a name match on a different domain is rejected, never used. Queries the full domain first, retries once on the bare label. The key is the platform provider **`logo-dev-secret`** (the `sk_...` SECRET key) — NOT `logo-dev`, which holds the PUBLISHABLE `pk_...` token used to build `img.logo.dev` image URLs and does NOT authenticate Search. Every failure here (key not registered, network, non-2xx, non-array body, no domain match) logs loudly and returns `null` so link 2 runs — an explicit fall-through with a guaranteed terminal fallback, not a swallowed error. A missing key must never fail a brand create.
2. **Landing page HTML** — `fetch` of the landing URL (browser User-Agent, 5s timeout), parsed by `parseBrandNameFromHtml`: `og:site_name` → `<title>` (site-suffix trimmed) → JSON-LD `Organization`/`WebSite` `.name`.
3. **Titlecased domain** (`titlecaseDomain`) — guaranteed non-empty terminal fallback.

**The chain runs at CREATE, not on read.** `getOrCreateBrand` → `fillBrandNameOnCreate` awaits ONLY link 1, so `POST /orgs/brands` returns a real `name` (never null) without ever waiting on a fetch of the customer's own website. On an index miss it persists the titlecased domain immediately and fires `upgradeProvisionalBrandName` in the BACKGROUND (link 2), whose UPDATE is conditioned on `name = <that exact placeholder>` — so a real name (user-set, or another writer's) is never clobbered. `persistBrandNameIfAbsent` writes only `WHERE name IS NULL` and returns whatever the row ends up holding, so **a stored name is never re-derived or overwritten**.

`ensureBrandName()` remains the read-path safety net (`GET /internal/brands/:id` etc.) for rows created before this — it runs the same chain and keeps `name` non-null on brand-detail reads. The `NODE_ENV === 'test'` bypass skips ALL network (index + landing fetch): the read path persists the raw domain, the create path persists the titlecased domain.

Regression: `tests/unit/logoDevSearch.test.ts` (match discipline, key absent, transport failures), `tests/unit/brandNameIndex.test.ts` (chain order on both paths, background upgrade, no-overwrite), `tests/integration/ensureBrandName.test.ts`.

Concurrency on the read path is still coordinated: multiple null-name reads share one in-process singleflight `Map<brandId, Promise<string>>` (`inFlightBrandNameFills`); Railway runs one instance, so this is acceptable — replace with a DB/advisory lock if brand-service becomes multi-instance. Always re-read `brands.name` after entering the fill gate before fetching.

**Field extraction** (`fieldExtractionService.extractFields`, the services / full-profile path — distinct from name-fill) selects its model by `urlStrategy`: `landing` → `flash-pro` (Gemini 3.5 Flash) + `disableThinking: true` (floors Gemini 3 thinking to "minimal" = cheap + fast; the single-page "sellable services vs internal steps" discrimination needs judgment `flash` was too weak for — do NOT remove `disableThinking`, that defaults Gemini 3.5 Flash to HIGH thinking); `url_map` → `pro`, chat-service default bounded thinking (deep multi-page background profile). **Scraped page content is capped at 100k chars/page (≈25k tokens) with NO global combined-content cap** — page counts are bounded (`landing` = 1, `url_map` ≤ 10 → worst case ~1M chars, fits Gemini's context); the prior 15k/page cut sliced services listed lower on long landing/pricing pages. (Set 2026-07-09, #329.) **Both paths send a strict `responseSchema` built by `buildFieldsResponseSchema(keys)`** — a Gemini-compatible object schema (every key `required`, each value `anyOf:[string, array<string>]`, deliberately NO `additionalProperties:false` which Gemini 400s on). This is load-bearing: without it the url_map 19-field extraction sent free-form JSON, Gemini 3 Pro flaked and emitted malformed/truncated JSON mid-output, and chat-service strict-parsed it to a **502 "Model returned malformed or truncated JSON"** (a char position well under the token cap = genuine model malformation, NOT a MAX_TOKENS truncation). The sibling `multiBrandFieldExtractionService.consolidateFields` carries the same schema. `thinkingBudget` is DEAD on the /complete path — chat-service only honors `disableThinking`; never re-add a `thinkingBudget` param to a `chat()` call. (Set 2026-06-29, v0.43.1 #306.) Its URL selection has three distinct states:
- `{"urls":[]}` is valid: the LLM found no relevant pages. Store `Unknown` with `sourceUrls: []` and do not scrape.
- Malformed URL-selection output is a backend error. Do not silently fall back to homepage/first 10 URLs.
- URLs selected but 0 usable page content is a scraping failure. Throw a diagnostic error with selected/cached/fresh/empty counts and the affected URLs.

Observed 2026-06-09 (new brand `luxvillageseminyak.com`): parallel name-fill runs (then LLM-based) caused one `/internal/brands/:id` request to 500 with opaque `Failed to scrape any pages`. The deterministic fill removes that failure mode for names entirely.

**`extract-fields` has TWO behaviors via the optional `mode` body param (`ExtractFieldsRequestSchema.mode: 'extract'|'suggest'`, default/omitted = `extract`), honored on BOTH `/orgs` and `/internal` routes.** `extract` = today's site-grounded extraction, returns `"Unknown"`/`["Unknown"]` when the info is absent (BYTE-IDENTICAL to pre-mode — the extract-branch prompt is untouched). `suggest` = the prompt flips to an Alex-Hormozi + top-3-industry-expert generative persona (`extractFieldsFromContent` branches on `mode`) that writes a best-effort value for EVERY field, inferring from the business where the source is silent, and NEVER returns `"Unknown"`/empty — while forbidding fabricated absurd/false/unverifiable specifics (invented numbers, named customers, guarantees). Both modes keep `temperature:0`, the same `responseSchema`, the same model-by-`urlStrategy` selection, and the same date/urgency guard. **Cache isolation is by SALTED hash: `hashFieldDescription(description, mode)` — `extract` hashes the raw description (byte-identical key → every existing `brand_extracted_fields` slot stays valid, no re-extraction churn on deploy), `suggest` salts the input → a disjoint hash space, so a suggest value is NEVER served to an extract request or vice-versa.** `mode` threads: schemas.ts → both routes → `multiBrandExtractFields` → `extractFields` (`getCachedFields`/`upsertExtractedFields`/`extractFieldsFromContent`) + the cross-brand `consolidateFields` prompt + `buildConsolidatedCacheKey`. In `suggest` mode the `selectedUrls.length === 0` "store Unknown" shortcut is bypassed (falls back to the landing page) so the never-Unknown contract holds. Regression: `tests/unit/extractionSuggestMode.test.ts`. Reference: PR (this branch).

## "Write it again from my website" needs the confirmed value withheld in BOTH places, and only for the keys asked for

A caller can ask to REGENERATE a confirmed field — `regenerateFieldKeys: string[]` on `POST /orgs|internal/brands/extract-fields`. Without it the button is inert by construction, because the confirmed value is used TWICE: `profileContext.buildProfileContextBlock` injects it into the prompt under an instruction to PREFER it over the scraped site, and then `multiBrandExtractFields` overlays it back over whatever the model produced. Suppressing one and not the other still hands the user their own previous input, so both suppressions ride the same flag — plus the extraction cache, whose stored value was itself produced under the poisoned prompt.

**The suppression is SCOPED to the listed keys, and that is the whole point.** The 6 Hormozi levers are written FROM the brand's confirmed `services`, so regenerating the levers must still show the model the confirmed services. Never widen this to "drop the confirmed layer for the request" — `extractFields` filters `confirmedFields` by key before building the block, and the overlay loop skips only the listed keys.

**Default behaviour is byte-unchanged.** No flag → the block carries every confirmed field and the overlay applies as before. This is not a mode and must not become the default: the other callers of extract-fields (content generation, internal service reads) want the confirmed value to win.

**A regenerated key is tagged `suggested`, not `confirmed`** — the returned value IS an unsaved auto-extract prefill for the caller to review, and calling it `confirmed` would claim the user validated something they have not seen. **Nothing is persisted or cleared**: `brand_user_fields` is untouched, the confirmed value still wins on every other read, and the user's save (`PUT /orgs/brands/:brandId/user-fields`) is the only thing that overwrites it. The one write is the ephemeral `brand_extracted_fields` slot for the regenerated key, refreshed with the new draft — which is correct, since the stale slot was the poisoned one.

**Every listed key MUST also be in `fields` → 400 (`UnrequestedRegenerateFieldKeyError`), before any work.** A key that is not being extracted has nothing to regenerate, so honouring it silently would tell the caller a field was refreshed when it was never touched.

api-service proxies the body verbatim (`brand.ts` forwards `restBody` with no schema parse), so no gateway change is needed — verified against `origin/main`. Its OpenAPI request schema re-declares a subset and predates `mode` too; that is a doc gap on the gateway, not a runtime one. Regression: `tests/unit/regenerateConfirmedFields.test.ts` (prompt + cache), `tests/unit/regenerateConfirmedOverlay.test.ts` (overlay, provenance, validator), `tests/integration/regenerateConfirmedFields.test.ts`.

## Two-layer brand fields: `brand_user_fields` (confirmed, durable) vs `brand_extracted_fields` (auto, 3-day TTL) + provenance

Brand fields are TWO layers, and every field returned to a consumer carries a **provenance** tag:

- **7 user-facing "confirmed" fields** — `services`, `dreamOutcome`, `perceivedLikelihood`, `socialProof`, `riskReversal`, `urgency`, `scarcity` (hardcoded `USER_FACING_FIELD_KEYS` in `src/services/brandUserFieldsService.ts`). The user validates these in the dashboard; they persist in **`brand_user_fields`** (one row per `(brand_id, field_key)`, DB CHECK on the 7 keys, NO TTL, `value` jsonb). `dreamOutcome` REPLACED the old `valueProposition` in the user-facing set — `valueProposition` is now a pure backend-extract field only (don't reintroduce it as user-facing; the icpSuggestion denylist etc. still reference it legitimately).
- **Everything else** = auto-extracted, ephemeral 3-day cache on `brand_extracted_fields` (unchanged; `CACHE_DURATION_MS` untouched).
- **Provenance**: `confirmed` (a user-facing field with a saved `brand_user_fields` value) | `suggested` (a user-facing field NOT yet confirmed — value = the auto-extract prefill) | `extracted` (a pure backend field).

**Endpoints** (`src/routes/user-fields.routes.ts`, orgRouter, mounted in `index.ts` AND `tests/helpers/test-app.ts`):
- `GET /orgs/brands/:brandId/user-fields` → `{ fields: { <key>: { value, provenance } } }` for all 7 keys. Confirmed value wins; else most-recent NON-EXPIRED `brand_extracted_fields` prefill (campaign_id IS NULL, expires_at NULL-or-future), else null. Does NOT trigger extraction.
- `PUT /orgs/brands/:brandId/user-fields` body `{ fields: Record<key,value> }` → `upsertUserFields` (validates every key ∈ the 7 → 400 `UnknownUserFieldKeyError` on any unknown key, NOTHING written), returns the GET shape.
- `POST /orgs/brands/extract-fields` response gained an ADDITIVE sibling `provenance: Record<key, 'confirmed'|'suggested'|'extracted'>` (built in `multiBrandFieldExtractionService`). Confirmed values overlay `fields[key].value` (single brand) + `byBrand[domain][key].value`; the existing `fields` value SHAPE is unchanged (content-generation-service reads `fields` directly and must keep working). A user-facing key tags `confirmed` only when EVERY brand in the request has a confirmed value, else `suggested`.

`brandProfileService.getByBrandId` now returns `{ current: { fields }, hasConfirmed, confirmedFields }` (was `{ current: version|null, versions[] }`). `current.fields` = confirmed overlaid on the derived-from-extracted fields; `confirmedFields` = the confirmed layer alone (the ONLY client-validated truth injected into the extraction prompt — `profileContext.buildProfileContextBlock` gates on `hasConfirmed`, NOT the merged fields, so we never feed our own past extractions back as authoritative). The versioned `brand_profile_versions` table + the standalone `/orgs/brands/:brandId/brand-profile` GET/POST were DROPPED (migration `0041`); the new confirmed store is the replacement. (A temporary backward-compat shim re-exposed `/orgs/brands/:brandId/brand-profile` over `brand_user_fields` while the prod dashboard + features-service migrated; it has since been fully removed — the only endpoints now are `/user-fields` GET/PUT. Do NOT re-add a brand-profile route.)

**Cron**: `index.ts` runs a daily `setInterval` (24h, + one run 60s after boot) AFTER `app.listen()` deleting `brand_extracted_fields WHERE expires_at < NOW()`. Confirmed rows live in `brand_user_fields` (different table) so they're never touched. Reference: PR (this branch).
